# 《吃的营养科学观》EPUB 双页首屏调查

## 2026-09-20 章节边界改造复核

上一版“分批挂载整书”的缓解方案已进一步收敛为章节级按需加载：连续滚动打开时只解析并挂载当前 spine 项；到达章节边界后，才读取下一项并替换当前 `.epub-chapter`。因此不会在首屏后台继续创建整本书 DOM，也不会让滚动事件触发跨章节加载。

本次浏览器回归验证了：首章唯一挂载、下一章切换后仍唯一挂载、上一章恢复、TOC/内链目标章节加载、章节本地阅读位置恢复以及跨章节划线导出。可选真实样本用例已改为连续滚动模式；没有配置本地样本时保持跳过，不能替代 fnOS 真机验收。

## 样本与复现条件

- 样本：用户提供的本地 EPUB；未复制进仓库或构件。
- 压缩包：4,237,499 bytes；159 个条目；解压总量 4,832,773 bytes。
- 结构：126 个 spine 项（封面、目录、124 个 HTML 分片）、24 张正文 JPG、约 204,235 个文本字符。
- 浏览器复现：Chromium，1280×800，预先保存“双页模式”后直接打开；另以 CDP 4× CPU 降速模拟低性能设备。

## 结论

这不是 EPUB 损坏、CPU 架构不兼容、资源超过限制，或“下一页”按钮本身失效。

旧实现把全部 126 个章节的 HTML 在一次 `article.innerHTML = …` 操作中插入。浏览器必须在同一个主线程任务里构建整棵 DOM、匹配样式并布局整书；双页模式随后计算多栏轨道和 890 个单页。4× CPU 降速下，首次打开会出现 3.27–3.62 秒的长任务，fnOS 浏览器上会表现为页面暂时无法响应。

去掉样本全部 24 张 JPG 后，最长任务仍约 3.63 秒，证明图片不是主因；图片只增加总加载时间。该书的特殊点是章节分片数和一次性整书 DOM 布局规模，而不是其 4.24MB 文件大小。

## 修复

- EPUB 解析保留章节数组，不再只保留整书 HTML 字符串。
- 阅读器每批挂载 4 个章节，批次间让出浏览器主线程。
- 批量挂载结束前不测量不完整的多栏轨道；完成后统一分页、恢复进度并重绘标注。
- 排版期间显示 `正在排版 n%（n/总章节）`，并禁用前后页按钮，避免把尚未完成的排版误认为翻页失效。

## 结果

在同一真实样本、预先双页、4× CPU 降速条件下：

| 项目 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 最长浏览器主线程任务 | 3.27–3.62 秒 | 0.64 秒以内 |
| 双页布局 | 可能被长任务阻塞 | 完成后 `1-2 / 890` |
| 首页下一页 | 可能没有可见响应 | 正常进入 `3-4 / 890` |

真实样本调查用例要求显式提供本地文件路径，默认 CI 不携带该 EPUB，也不会将其内容写入仓库。

## Task 4 回归与当前复验状态

章节窗口实现改变了旧调查中的页码语义：分页轨道和状态仅描述当前挂载的 spine 章节；到达该章节的最后分页组后，“下一页”异步加载下一个 spine 项，并以新的 `.epub-chapter[data-source-path]` 替换当前章节。DOM 的章节数保持为一，不再以整书 `890` 页作为当前实现的进度语义。

新的本地可选回归有两条：

1. 在 `ZHENSHU_E2E_CPU_THROTTLE=12` 下，8 秒内必须出现唯一、稳定的 `.epub-chapter`：有可见非空文本，或有实际可见且已解码的媒体（`img.complete && naturalWidth > 0`，或有效 SVG/canvas）；状态不得匹配 `/^正在打开/`，分页 geometry/track 已就绪，`#article[aria-busy]` 已清除，并且可用下一页或下一章动作。
2. 在 4× CPU 降速下，从 `data-pagination-track` 读取 `groups=`，逐组进入当前章节的最后一页，点击下一页后要求 `data-source-path` 改变；改变后再次等待唯一、可见非空内容、非 loading 状态、分页 geometry/track 和非 busy 导航全部稳定，才读取 long task，且最大值不超过 1000 ms。

2026-09-19 尝试使用指定路径 `C:\Users\admin\Desktop\吃的营养科学观.epub` 运行时，该文件不存在。首次运行的两个用例均在等待书库条目时达到 30 秒超时；根因检查 `Test-Path` 返回 `False`，且 Desktop/Downloads 中未找到匹配 EPUB。E2E 启动器现会在路径相对或文件缺失时立即失败，错误为 `ZHENSHU_E2E_SAMPLE_EPUB does not exist: <path>`，不会把缺失夹具伪装为产品回归结果。

上述缺失路径是历史失败，不是当前状态。样本恢复后，旧的“仅文本”首章谓词还曾错误拒绝正确显示的 cover-only `titlepage.xhtml`；该失败也保留为历史 RED 证据。现行谓词验证解码后的可见媒体，因此不会把隐藏、透明、零尺寸或未完成解码的图片当作内容。

恢复后的最终真实样本复验已完成：完整 12× 命令 **2 passed (20.7s)**，首章 `openedMs=4293`、最大 long task `530 ms`，章节边界最大 `498 ms`；完整 4× 命令 **2 passed (9.5s)**，首章 `openedMs=1261`，章节边界 `titlepage.xhtml → toc.xhtml`，最大 long task `524 ms`。两个边界测量都保持一个 mounted chapter，且均低于 1000 ms。复现命令仍为：


## 其他检查

- OPF 中的 `scripted` 标记来自导出工具；阅读器会移除 `script`、`iframe` 等可执行内容，未发现脚本执行路径。
- 样本 CSS 为常规 Calibre/Joplin 导出样式，未发现导致无限布局的异常 `position`、极端尺寸或嵌套列规则。
- 资源预算保护没有命中：24 张 JPG 总计约 4MB，低于单项 8MB、总量 48MB 的保护阈值。

## 已知边界

分批挂载把“冻结”改为可见、可交互的排版过程，但在明显更慢的设备上，整书完成仍需要时间。若后续样本达到数百章节或数百万字符，下一阶段应采用章节级虚拟化/按需分页，而不是继续增加单次 DOM 的容量。

当前章节窗口已经采用按需单章节加载；它仍需要真实 fnOS 设备安装新 FPK 后，使用本书完成首章打开、章节边界、划线和进度的物理设备验收。

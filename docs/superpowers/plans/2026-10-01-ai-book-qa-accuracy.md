# AI 问书：准确、高效、低成本方案（调研与规划，未执行）

日期：2026-10-01 状态：待用户确认

## 1. 现状诊断：为什么“总结不了全书、对不准章节”

以下问题都已在代码里核实（括号内为位置）。

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | 章节概述、全书概述默认**关闭**：`cmd/main` 设 `ZHENSHU_ENABLE_AI_CHAPTER_UNDERSTANDING=0`，关闭时“总结全书/本章”被降级成普通检索（`index.js` `effectiveAiIntent`） | 问“这本书讲了什么”，实际只拿到 6 段零散原文，回答必然片面 |
| 2 | 章节原文上限 22,000 字、最多 8 个 3,000 字分段（`ai-chapter-retrieval.js` `MAX_CHAPTER_SOURCE_CHARS`、`MAX_MAP_TASKS`），超过直接报 413 | 中文书一章常有 1–4 万字，大量章节“超出预算” |
| 3 | 全书概述只抽 8 个“代表章节”，每次提问现场 map-reduce，缓存键含问题原文（`prepareBookSummary`） | 慢、贵、覆盖不全；换个问法就重新花钱 |
| 4 | 普通问答只给模型 6 段 × 900 字 ≈ 5,400 字（`AI_CONTEXT_CHAR_BUDGET`） | 现在主流模型有 128K–1M 上下文，证据给得太少 |
| 5 | 检索是纯字面：中文按两字切分后用 OR 拼成 FTS 查询（`ai-fts.js` `aiTerms`/`toFtsQuery`），问题里的“这本书”“作者”“什么”等也参与匹配 | 召回噪声大；同义、概念类问题（“作者怎么看待……”）找不准 |
| 6 | 意图识别全靠正则（`classifyAiIntent`）：“第三章讲了什么”“《xx》这一节”“前面提到的那个人”等识别不了 | 范围判断错，答非所问 |
| 7 | 书的“结构”只有 EPUB 有（`readChapterEvidence` 仅支持 epub）；TXT/Markdown 没有章节；PDF 另一套流程 | 跨格式效果不一致 |
| 8 | 只支持 OpenAI `/responses` 接口（`ai-service.js`） | DeepSeek、通义、Kimi、智谱、本地 Ollama 等多数便宜的国产模型主要提供 `/chat/completions`，用户被迫选贵的或用中转 |
| 9 | 选中文字提问时，只把选中文字作为加权检索词 | “指哪答哪”缺少选区前后文和所在章节的背景 |

结论：问题主要不在模型，而在**“给模型什么材料”**：没有全书/章节层面的“地图”，章节读不完，检索给得少且不准。

## 2. 开源项目与业界做法调研

| 方案 | 做法 | 对“问书”的适用性 | 成本 |
| --- | --- | --- | --- |
| 微信读书 AI 问书 / AI 大纲 | 选中文字或搜索即问；另有 AI 生成的结构化大纲 | 体验标杆：“指哪答哪”+全书大纲 | 平台级预处理 |
| [PageIndex](https://pypi.org/project/PageIndex/)（VectifyAI） | 不用向量：先生成带摘要的目录树，问答时让模型沿目录树推理选节点，再读原文 | 很适合书：书本来就有目录；FinanceBench 98.7% | 预处理一次 LLM；问答时多一次“导航”调用 |
| [RAPTOR](https://proceedings.iclr.cc/paper_files/paper/2024/hash/8a2acd174940dbca361a6398a4f9df91-Abstract-Conference.html)（ICLR 2024） | 把文本块递归聚类、逐层摘要成树，检索时同时用摘要和原文 | 专治“需要整合全书信息”的问题（NarrativeQA、QuALITY 上提升明显） | 预处理一次 LLM |
| [RAGFlow](https://ragflow.io/docs/configure_child_chunking_strategy) | “Book”切分模板；目录增强；父子分块（小块用于召回，大块用于作答） | 父子分块思路可直接借鉴 | 低 |
| [Anthropic Contextual Retrieval](https://anthropic.com/news/contextual-retrieval) | 每块前加 50–100 字“这块在全文中的位置/背景”再建 BM25 和向量；加重排后检索失败率降 67% | 书有现成目录，可**零成本**加“书名 › 章 › 节”前缀，拿到大部分收益 | 简化版无额外成本 |
| [PaperQA2](https://docs.edisonscientific.com/paperqa) | 检索后让 LLM 对每块打分并做“针对问题的摘要”，再作答 | 准，但每问多次调用 | 较高 |
| ReadAny（开源 AI 阅读器，GPL-3.0） | 向量 + BM25 混合检索，向量存本地 SQLite | 说明“本地 SQLite + 混合检索”在阅读器里可行 | 需嵌入模型 |
| GraphRAG / [LightRAG](https://arxiv.org/pdf/2506.05690) | 抽实体关系建知识图谱 | 一本短书 GraphRAG 约 $4–7，LightRAG 约 $0.15，主要利好“人物关系”类问题 | 偏高，暂不采用 |
| 长上下文直塞 | 整本书放进 1M 上下文 + 前缀缓存（如 [DeepSeek V4 缓存命中价约为未命中的 1/50](https://www.morphllm.com/deepseek-api)） | 小书可行；但首问慢、中段信息易丢、依赖特定厂商 | 首问贵，后续便宜 |

取舍：**PageIndex 的“沿真实目录导航” + RAPTOR 的“分层摘要” + RAGFlow 的父子分块 + 简化版上下文检索**，正好对应本项目已有的目录解析、SQLite FTS 索引和摘要缓存，改造成本最低；向量检索作为可选增强；GraphRAG 不做。

## 3. 推荐方案：“书籍导读图”（Book Map）+ 先导航后检索

### 3.1 总体流程

```
建索引（已有，增强）           生成导读图（一次性、可共享）          每次提问
EPUB/MOBI/PDF/TXT/MD           按真实目录逐节摘要                    ① 路由：规则 → 不确定时用目录做一次轻量“导航”
→ 目录树 + 原文块            → 汇总成章摘要 → 全书摘要            ② 按问题类型取证据
→ FTS（+ 可选向量）           → 关键词/人物/概念                     ③ 稳定前缀（书卡）+ 证据 + 问题 → 作答（带引用）
```

### 3.2 导读图（新增，核心）

- 结构：所有格式统一成目录树。EPUB 用现有 nav 解析；PDF 用书签，没有书签时用现有版面结构；TXT/Markdown 新增标题识别（“第X章/节”、`#` 标题、空行加短行）。
- 节点：每个叶子节（约 ≤6,000 字，过长的再按段切）生成 150–300 字摘要和 5–10 个关键词/人物/概念；章摘要由节摘要汇总；全书摘要由章摘要汇总，同时得到一份“AI 大纲”。
- 存储：写入每本书现有的 SQLite 索引（新表），按“书指纹 + 模型 + 提示词版本”缓存。**同一台 NAS 上所有用户共享**（只依赖书的内容，不含个人信息），不再按用户、按问题重复生成。
- 触发：首次问到“全书/章节”类问题时，只生成需要的部分（懒生成）；书的 AI 索引管理里加“生成导读”按钮，生成前显示预计字数和费用，可中断、可续跑。不自动给全部书批量生成，避免意外花钱。
- 模型：新增“经济模型”设置（用于摘要和导航，如 DeepSeek V4-Flash、qwen-flash），作答可以用更好的模型。

### 3.3 提问时的路由（解决“对不准章节”）

1. **规则先行（免费）**：扩展现有正则，并把“第 N 章 / 章节名 / 本章 / 这一节 / 选中文字”与目录标题做模糊匹配，直接定位到节点。
2. **不确定时一次轻量导航调用**：把问题 + 精简目录（每节一行摘要，约 1,500–3,000 token）交给经济模型，返回 JSON：问题类型、相关节点、改写后的检索词。这就是 PageIndex 的思路，但目录只有一屏，成本很低。
3. 问题类型及取证方式：

| 类型 | 例子 | 证据 |
| --- | --- | --- |
| 全书概览 | 这本书讲了什么 / 核心观点 | 全书摘要 + 各章摘要（现成，问答时零 map-reduce） |
| 章节概述 | 第三章讲了什么 / 本章要点 | 章摘要 + 节摘要；整章不超过预算（如 4 万字）就直接给全文，超过才用节摘要 + 章内检索；去掉 22,000 字硬上限 |
| 定位事实 | 作者在哪里提到 X / X 是什么 | 检索（限定在导航选出的章节内优先）→ 命中块扩展到前后段落（父子分块）→ 附“书名 › 章 › 节” |
| 指哪答哪 | 选中一句话：“这里是什么意思” | 选区 + 前后各约 1,500 字 + 所在节摘要 + 全书一句话摘要；选区里的概念再检索“首次出现/定义处” |
| 跨章比较 | 第一章和第五章观点有何不同 | 相关各章摘要 + 各章内检索 |

### 3.4 检索增强（低成本优先）

- 查询清洗：把“这本书、作者、什么、请问”等问句套话从检索词中去掉（现有 `chapterSearchTerms` 推广到所有检索）；用导航返回的改写检索词。
- 排序：FTS5 改用 `bm25()` 加权（标题/小标题权重已有），减少全 OR 带来的噪声；按章节多样性去重。
- 上下文前缀：索引和给模型的文本都带“书名 › 章 › 节”（简化版 Contextual Retrieval，无额外调用）。
- 证据预算：从 5,400 字提到按模型上下文自适应（默认约 2–3 万字），并按“问题类型”分配。
- **可选**向量检索：用户在设置里填 OpenAI 兼容的 `/embeddings`（百炼 text-embedding-v4、硅基流动 bge-m3、本地 Ollama 均可）。一本书约 400 个块，向量以二进制存进现有 SQLite，查询时在 Node 里直接算余弦（毫秒级，不需要 sqlite-vec 等原生扩展，避免 fnOS 跨架构打包问题），用已有的 `fuseRankedMatches`（RRF）与 FTS 融合。默认关闭，评测证明有收益再推荐。
- 重排：默认不加（导航限定范围后收益有限）；评测后再决定是否支持可选的重排接口。

### 3.5 提示词布局（吃满前缀缓存）

固定顺序：系统指令 → **书卡**（书名、作者、全书摘要、精简目录；同一本书每次都一样）→ 本次证据 → 对话历史 → 问题。DeepSeek、通义、OpenAI 等的自动前缀缓存会让书卡部分在同一本书的连续提问里按缓存价计费。回答继续要求 [n] 引用，可点击跳回原文。

### 3.6 接口兼容（直接决定成本）

新增 `/chat/completions` 支持（流式），保留 `/responses`。设置里选“接口类型”，或“测试连接”时自动探测。这样 DeepSeek、通义千问、Kimi、智谱、硅基流动、本地 Ollama 都能直接用。

| 方案 | 一次性成本 | 每问成本 | 首字延迟 | 全书/章节问题质量 |

## 5. 分阶段计划（每阶段先评测再上线）

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| P0 评测基线 + 接口兼容 | 选 4–5 本书（EPUB 小说、EPUB 社科、扫描质量好的 PDF、TXT），每本 15 题，覆盖上表 5 类问题，共约 70 题；扩展现有 `scripts/evaluate-ai-*.js` 统计：路由正确率、证据命中率、回答正确/忠实度（带引用核对）、token、延迟、费用。新增 `/chat/completions` 与“经济模型”设置 | 得到现状分数；DeepSeek/通义可直接配置使用 |
| P1 统一目录树 + 路由 | TXT/MD 标题识别、PDF 书签；规则路由扩展 + 轻量导航调用；去掉 22,000 字上限，章节在预算内给全文；默认开启章节/全书理解 | 显式章节问题路由正确率 ≥ 95% |
| P2 导读图 | 节/章/全书摘要生成、共享缓存、懒生成 + “生成导读”按钮（显示预估费用）；全书概览直接用导读图；目录面板可显示“AI 大纲” | 全书/章节概述合格率 ≥ 85%，每问平均 ≤ ¥0.02 |
| P3 检索与“指哪答哪” | 查询清洗、bm25、父子分块扩展、书卡前缀缓存布局、选区邻域证据 | 定位事实类证据命中率较 P0 明显提升；选中提问合格率 ≥ 90% |
| P4 可选向量 | `/embeddings` 设置、向量入库、RRF 融合；评测决定是否推荐默认开启 | 概念/同义类问题有可测提升才保留 |
| P5 PDF 与深度模式（可选） | PDF 页码引用、无书签时的结构推断；为支持超长上下文的模型提供“深度阅读”开关（整章/整书直塞） | 视评测与需求决定 |

建议先做 P0–P2：能直接解决你提到的“概括不了全书、对不准章节”，且不引入新依赖。

## 6. 需要你确认的决定

1. **导读生成时机**：懒生成 + 手动“生成导读”（推荐），还是新书入库后自动在后台生成（省等待，但会自动花费 API 费用）？
2. **导读是否全 NAS 共享**：推荐共享（同一本书只花一次钱）；生成时使用触发者自己的 API Key。
3. **向量检索**：作为可选项（推荐），还是暂不做？
4. **推荐默认模型**：建议把 DeepSeek V4-Flash 这类便宜、长上下文、带缓存的模型作为示例配置（需先完成 `/chat/completions` 兼容）。

## 7. 风险

- 摘要可能遗漏或失真：摘要只用于导航和概览，具体事实一律回原文取证并标引用；摘要带版本号，可一键重建。
- 小模型导航出错：规则优先；导航结果不确定时退回全书检索；评测集持续回归。
- 扫描版 PDF 没有文字层：本方案不含 OCR，界面上明确提示。
- 价格会变：成本以 token 量为准，界面显示的是 token 预估。

## 8. 用户决定（2026-10-01）

1. 导读：**首次问到时生成 + 手动“生成导读”按钮**。
2. 导读**全 NAS 共享**（按书的内容缓存，不按用户）；生成时用触发者自己的 AI 配置。
3. **做语义检索**（可选配置，填了嵌入模型才启用）。
4. 只用 **OpenAI 协议**，模型由用户自己添加：默认走 `/chat/completions`，保留 `/responses` 作为选项；不内置任何厂商预设。

## 9. 开发计划（按阶段执行，每阶段：实现 → 单元测试 → 评测 → 全量回归 → 提交，然后自动进入下一阶段）

### P0 接口兼容、用量统计、评测基线

- 0.1 `ai-transport.js`：把现有 Responses 形态的请求转换成 `/chat/completions`（system/messages、`max_tokens`、`response_format: json_object`、流式 `choices[].delta.content`），统一解析非流式和流式返回，并读取 `usage`。`requestOpenAiAnswer`、`requestOpenAiStream`、`testOpenAiConnection` 改走它。
- 0.2 AI 配置新增：`apiFormat`（`chat` | `responses`，新配置默认 `chat`；旧配置没有此字段时按 `responses`，保持原行为）、`summaryModel`（导读/导航用的经济模型，留空同主模型）、嵌入配置（`embeddingModel`，`embeddingBaseUrl`/`embeddingApiKey` 留空同主服务）。设置界面增加对应字段。
- 0.3 用量：回答结束事件附带本次 token 用量，供评测和后续界面使用。
- 0.4 评测：`tests/fixtures/ai-book-qa/` 生成一本有明确章节、小节和可核对事实的测试书（EPUB + TXT），配 30 道题，覆盖全书概览、章节概述、定位事实、选中解释、跨章比较；`scripts/evaluate-ai-book-qa.js` 离线统计路由正确率和证据命中率，设置 `ZHENSHU_EVAL_API=1` 与 AI 配置后可做真实模型评测（回答评分、token、耗时）。记录现状基线。
- 验收：两种接口的单元测试（含模拟上游的流式/非流式/错误）通过；基线数字写入本文档。

### P1 统一目录树 + 路由 + 服务端取证

- 1.1 索引 schema 升级：按段落切块、不再重叠（约 800 字）；每块记录所属最细节点；新增 `ai_nodes` 表（id、父节点、层级、顺序、标题、首尾块号、字数）。EPUB 用现有目录解析；TXT/Markdown 新增标题识别（`ai-text-structure.js`）。
- 1.2 节点读取：按节点取全文（带上限）、取目录树。
- 1.3 规则路由（`ai-router.js`）：识别“第 N 章/卷/节”（含中文数字）、章节名模糊匹配、本章/本节（结合阅读位置）、选中文字、全书、比较。
- 1.4 导航调用：规则不确定时，用经济模型 + 精简目录返回 JSON（类型、节点、检索词），8 秒超时后退回规则结果。
- 1.5 服务端取证（`ai-evidence.js` + 问答流水线）：客户端不再上传上下文，只发问题、选区、阅读位置；服务端路由、取证、作答。章节问题整章不超过预算（默认 4 万字）就给全文。保留旧的“客户端带上下文”接口兼容旧测试。移除 `ZHENSHU_ENABLE_AI_CHAPTER_UNDERSTANDING` 开关，章节/全书理解默认开启。
- 1.6 前端：改用新流程；显示“依据范围”（全书导读/某章/选中段落）；显示进度事件。
- 验收：显式章节问题路由正确率 ≥ 95%（评测集）；全部回归通过。

### P2 导读图

- 2.1 `ai-book-map.js`：节点摘要（叶子用原文，父节点用子摘要；长章先分段）、全书摘要；输出 JSON（摘要、要点、关键词/人物/概念）。缓存键：节点 id + 内容哈希 + 导读版本；存在书的索引库中，重建索引时按内容哈希沿用。
- 2.2 生成任务：每本书一个后台任务（并发 3、可取消、可续跑、进度）；提问时只懒生成需要的节点并推送进度。
- 2.3 接口：查询导读状态与大纲、预估字数和 token、开始/取消生成。
- 2.4 界面：AI 面板新增“导读”页：全书摘要 + 章节大纲（可跳转）、“生成导读”按钮（显示预估）、进度。
- 2.5 路由和取证使用导读：导航时附章摘要；全书概览直接用全书摘要 + 各章摘要。
- 验收：全书/章节概述在评测中合格；同一本书第二次概览提问不再产生摘要调用。

### P3 检索质量与“指哪答哪”

- 3.1 查询清洗（去掉问句套话）；FTS 先“全部命中”查询，再退回“任一命中”；bm25 排序。
- 3.2 命中块扩展到同节点前后相邻块；证据带“书名 › 章 › 节”。
- 3.3 选中提问：在书中定位选区，取前后各约 1,500 字 + 所在节摘要 + 全书一句话摘要。
- 3.4 提示词布局：系统指令 → 书卡（书名、作者、全书摘要、精简目录）→ 证据 → 历史 → 问题；证据预算按类型分配（默认约 2.4 万字）。
- 验收：评测中定位事实类证据命中率高于 P0；选中提问用例全部取到选区邻域。

### P4 语义检索

- 4.1 `ai-embeddings.js`：OpenAI `/embeddings` 客户端（分批、限长、超时）；向量按“块内容哈希 + 嵌入模型”存进索引库（Float32 二进制），重建索引时沿用。
- 4.2 填了嵌入模型后，在后台或导读任务中为书生成向量；提问时查询向量与块向量做余弦，取前 20，与 FTS 结果用 RRF 融合。
- 验收：评测中概念/同义类问题命中率不低于纯 FTS；未配置时行为与 P3 完全一致。

### P5 PDF 统一与收尾

- 5.1 PDF 用书签/标题结构生成节点，接入同一套路由、导读、检索（引用页码）。
- 5.2 文档、变更记录、全量回归。

真实大书压力测试（本地《剑来》EPUB，42 册、1,100 余万字）：

- 建索引约 9 秒，目录 474 个节点。
- 发现并修复了一个已有的解析错误：EPUB2 的 NCX 目录在条目闭合时才记录，子节点排在父节点之前，导致整本书的章节都挂到了上一册（如第一册的章节挂在“人物志”下）。现按开标签顺序记录，EPUB 解析版本升到 3。
- 分卷（“册”）识别：每册章节编号重新开始时，“第三章”优先取问题里写明的册（“第二册第三章”），其次取读者当前所在的册；都没有时标为低置信度，交给导航模型判断。
- 封面、制作说明、人名列表等不足 20 字的节点不参与匹配。
- 全书概览在 P1 只能抽样原文（超过 30 章时均匀抽 30 章，总量不超过 3 万字），P2 的导读图会取代这一做法。

### P2 结果：导读图

- 生成单元沿真实目录规划：不超过 2.4 万字的章整章读一次；更长的章先逐节摘要再汇总；分卷的书由章汇总到卷；最后由顶层各部分汇总全书（含“全书结构”和核心要点）。评测书共 9 次调用、约 4.5 万输入 token。
- 超长书按比例抽读：所有“读原文”单元的总量控制在约 120 万字以内（每单元不少于 4,000 字），例如《剑来》约 1,100 万字的书完整导读约 130 万输入 token。
- 存储：`<数据目录>/ai-map/<书ID>.json`，按“节点 + 内容哈希”缓存，全 NAS 共享；重建或清理检索索引不影响导读；书的文字变化后，对应节点自动重新生成。
- 懒生成：问全书时，若缺失部分预计不超过 25 万输入 token，就当场生成并推送进度（“正在生成本书导读（3/9）…”），之后直接复用；超过则先用抽样原文回答，并在“依据”里注明完整导读的预计用量和生成入口。问超长章节时只生成这一章（及其小节）。
- 使用：全书概览直接用“全书导读 + 各部分导读”（分卷书在预算内再加各章导读）；超长章节用“本章及各节导读 + 抽样原文”；比较时超长部分先给导读；选中提问附上所在小节的导读（已有时）；导航调用的目录附各章一句话导读；全书导读写进书卡，作为稳定前缀。
- 界面：AI 面板新增“导读”页，显示状态、预计用量、进度条，可生成/补全/停止/重新生成（重新生成前确认），展示全书导读与可展开的章节导读，并可跳回正文。PDF 暂不显示。
- 顺带：TXT/Markdown 书现在也能使用 AI 问书（此前前端只允许 EPUB 和 PDF）。
- 评测：离线指标不变（导读需要真实模型）；真实评测请设置 `ZHENSHU_EVAL_API=1` 和模型环境变量，`planned` 管线会先为评测书生成导读，再用与线上相同的回答提示词作答并评分。

### P3 结果：检索质量

- 问题清洗：去掉“这本书、作者、什么、请问、是谁……”等问句用语和虚词后再取关键词（“明前尖的价格是雨前茶的几倍” → 明前尖 / 价格 / 雨前茶）。
- 两段式检索：先找“每个关键词都出现”的段落（关键词内任一二字词命中即可，避免切词误差），不足 6 段时用“任一关键词命中”补足；严格检索落空时不再退回全书逐段扫描。
- 段落扩展：每个命中块连同前后相邻块合并成一段完整原文（去重叠），总量不超过 1.4 万字；交给模型的不再是被切断的 900 字窗口。
- 评测（离线）：定位事实类召回 100%（与 P1 相同），首条即命中答案 82%（与旧流程相同），每题证据约 0.9 万字（旧流程 0.4 万字的片段）。这本测试书较小，严格检索的排序收益要在大书上才明显；同义、换说法的问题（如“住了多少年”对应原文“住满七年”）留给 P4 语义检索。
